REFERENCE ARCHITECTURE 6-Stage Multimodal Evidence & Investigation Flow (Includes Proposed Extensions)

Pipeline Stages & Component Breakdown

  • Stage 1 — Issue Ingestion & Normalization Implemented PoC: Formats issue tracker records (PLM: Product Lifecycle Management), reproduction steps, device configurations, and attachment metadata into a structured, auditable issue package.
  • Stage 2 — Multimodal Symptom Understanding:
    Implemented in PoC Employs FFmpeg-based video frame extraction to sample temporal overview frames and dense suspect intervals.
    Proposed extension — not implemented or evaluated The proposed redesign would augment this with vision-language processing and OCR to extract timestamped UI transitions, isolating visible anomalies from reporter assumptions.
  • Stage 3 — Contextual Log Correlation Implemented PoC: Parses Android bug reports (logcat and dumpstate event sequences) around symptom timestamps to extract lifecycle events, system state transitions, and diagnostic clues.
  • Stage 4 — Hybrid Code & Documentation RAG:
    Implemented in PoC RAG integration over repository source code and feature documentation to supply relevant context for issue investigation.
    Proposed extension — not implemented or evaluated The proposed redesign would introduce Tree-sitter AST structural chunking combined with BM25 lexical search and dense vector embeddings in Qdrant, fused via Reciprocal Rank Fusion (RRF).
  • Stage 5 — Evidence-Grounded Reasoning:
    Proposed extension — not implemented or evaluated Conceptual component designed to synthesize collected video observations ([V]), log sequences ([L]), and code passages ([C]) under explicit evidence contracts. Under the proposed design, Samsung Gauss would be prompted to evaluate competing causal hypotheses and formulate verification checks. (Not evaluated in internal deployment).
  • Stage 6 — Module Routing & Developer Review:
    Proposed extension — not implemented or evaluated In the proposed design, candidate modules would map to responsible teams via an administrative ownership catalogue lookup, presenting an auditable triage summary for developer confirmation before ticket reassignment. (Not evaluated in internal deployment).

REFERENCE ARCHITECTURE On-Device Face Processing, Clustering & Offline P2P Transfer (Includes Proposed Extensions)

Pipeline Stages & Component Breakdown

  • Stage 1 — Offline Session Discovery & Photo Selection:
    Implemented in PoC Offline peer-to-peer discovery and photo selection allowing users to select local photos via Android Photo Picker without exposing full galleries.
    Proposed extension — not implemented or evaluated The proposed design would establish structured multi-device discovery using Google Nearby Connections (Cluster strategy) with automated cryptographic session handshakes.
  • Stage 2 — On-Device Face Detection & Landmark Alignment:
    Implemented in PoC On-device face detection to identify bounding boxes and extract crops locally.
    Proposed extension — not implemented or evaluated Would apply facial landmark affine transformation alignment to reduce pose and scale variance before model input.
  • Stage 3 — MobileFaceNet Feature Vector Generation Implemented PoC: Executes a lightweight pretrained MobileFaceNet model on-device to extract compact 128D face representations, normalizing output vectors to unit length. (ONNX Runtime packaging represents a proposed deployment target).
  • Stage 4 — Local Complete-Linkage Agglomerative Clustering Implemented PoC: Computes pairwise cosine distance (1 - u · v) across face embeddings and applies complete-linkage clustering with a calibrated distance threshold to group recurring appearances locally without cloud dependencies.
  • Stage 5 — Global Catalogue Consolidation (Coordinator):
    Proposed extension — not implemented or evaluated In the proposed architecture, participating phones would transmit only embeddings and low-resolution thumbnails to a session coordinator, which would re-cluster vectors across devices into a unified, anonymous person catalogue. (Not evaluated in internal deployment).
  • Stage 6 — Catalogue Distribution & Group Browsing:
    Proposed extension — not implemented or evaluated In the proposed architecture, the session coordinator would broadcast the consolidated person catalogue to all participants, enabling users to browse common face groups and select photos of interest without exposing unshared gallery images. (Not evaluated in internal deployment).
  • Stage 7 — Direct Peer-to-Peer Payload Transfer:
    Implemented in PoC Offline peer-to-peer transfer of selected photos between nearby devices.
    Proposed extension — not implemented or evaluated Would implement Nearby Connections high-resolution file payload channels with automated hash integrity verification after explicit user approval.

NLP BERT Text Classification Web Scraping
View Architecture Flowchart & Proposed Pipeline ▾

Implementation Status & Scope:

  • Implemented PoC Collaborative workplace proof of concept developed in a two-member team at Samsung R&D Institute Bangladesh Ltd. and evaluated through internal innovation reviews. Collected and categorized ~10,000 website links through web scraping, fine-tuned pretrained BERT on URLs and page descriptions, and demonstrated category-based tab grouping for Samsung Internet.
  • Proposed extension — not implemented or evaluated Dedicated Trafilatura main-text scraping, domain-disjoint 70/15/15 partitioning, a local FastAPI PyTorch evaluation service (torch.inference_mode()), and a browser extension review/undo UI represent a conceptual technical redesign and were not implemented or evaluated internally at Samsung.
REFERENCE ARCHITECTURE Dataset Funnel, BERT Fine-Tuning & Tab Delivery (Includes Proposed Extensions)

Pipeline Stages & Component Breakdown

  • Stage 1 — URL Discovery & Metadata Extraction Implemented PoC: Scraped ~10,000 candidate website URLs from topic listings and directories, downloading HTML and extracting page titles and meta descriptions for model training.
  • Stage 2 — Main-Text Extraction & Domain-Disjoint Partitioning:
    Proposed extension — not implemented or evaluated In the proposed design, Trafilatura would be used to extract clean page text while stripping scripts and boilerplate, and records would be partitioned strictly by registered domain (70% train, 15% validation, 15% test) to prevent publisher leakage across splits.
  • Stage 3 — Supervised BERT Fine-Tuning Implemented PoC: Tokenized packed inputs ([CLS] title + description [SEP]) under a token budget and updated encoder layers and a linear classification head using AdamW with weight decay to classify pages into topic categories.
  • Stage 4 — Fixed-Weight Local Inference Service:
    Proposed extension — not implemented or evaluated In the proposed design, the fine-tuned checkpoint would be loaded in PyTorch evaluation mode (torch.inference_mode()) behind a local FastAPI service for deterministic scoring without online parameter updates.
  • Stage 5 — Browser Tab DOM Snapshotting:
    Proposed extension — not implemented or evaluated In the proposed design, a browser extension would capture DOM text from active tabs while excluding pinned and internal browser pages.
  • Stage 6 — Reviewable Tab Grouping & Safe Undo:
    Implemented in PoC Demonstrated category-based grouping of related browser tabs.
    Proposed extension — not implemented or evaluated The proposed extension would provide an interactive preview interface for user adjustments alongside a stateful undo mechanism. (Not evaluated in internal deployment).
