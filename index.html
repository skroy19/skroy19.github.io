IssueLens

Samsung Research · November 2025

Multimodal AI-Assisted Bug Localization & Investigation

Investigating software issues often requires reviewing bug descriptions, watching reproduction videos, searching large device logs, and locating the responsible code.

Developed IssueLens to bring these sources together. It combines multimodal AI (visual failure inspection from reproduction videos and contextual device log parsing) with retrieval-augmented generation (RAG) over source code to suggest likely responsible modules, probable causes, and verification steps for developer review.

Key capabilities:

  • Multimodal investigation: Analyze bug descriptions, reproduction videos, and device logs together to understand the reported failure.
  • Module localization: Use RAG to connect issue evidence with relevant source code and feature documents to identify likely responsible modules.
  • Evidence-backed guidance: Suggest probable causes and verification steps with supporting evidence for developer review.

My contribution: Implemented the multimodal video analysis pipeline with FFmpeg frame extraction and RAG integration over source code and feature documentation to provide relevant evidence for issue investigation.

Multimodal AI Bug Localization RAG LLM FFmpeg Android Logs
View Architecture Flowchart & Two-Phase Pipeline ▾
ARCHITECTURE AT A GLANCE Phase A: Prepare Project Knowledge · Phase B: Bug Localization & Investigation

Phase A — Prepare project knowledge

The project's code and documents are indexed initially and updated as they change.

  • A1 | Collect code and documents: Read source code, feature requirements, and module information from known project revisions.
  • A2 | Prepare meaningful passages: Use Tree-sitter to extract code around method boundaries and split documentation into relevant sections.
  • A3 | Prepare search representations: Use BM25 for keyword matching and Qwen embeddings to retrieve passages with related meaning.
  • A4 | Store versioned knowledge: Store passages and source metadata in Qdrant, preserving the revisions needed for investigation.

Phase B — Investigate an issue

A developer provides a PLM issue number to start the investigation.

  • B1 | Collect issue materials: Retrieve the description, reproduction steps, affected version, videos, and device logs through a tracker connector.
  • B2 | Understand description and video: Extract timestamped frames with FFmpeg and use Gauss Vision to identify the visible failure.
  • B3 | Extract contextual log events: Use streaming parsers and contextual filtering to retain relevant events, identifiers, and surrounding records.
  • B4 | Retrieve code and documents: Combine keyword and semantic search to find relevant implementation passages for the affected release.
  • B5 | Investigate modules and causes: Gauss compares incident evidence with retrieved knowledge to suggest candidate modules, probable causes, and verification steps.
  • B6 | Report and developer review: Present findings with evidence references and known module owners for review before approved tracker updates.

SnapSync

Samsung Research · June 2026

Personalized and Simultaneous Photo Sharing System

Find photos of a chosen person across nearby phones, then download the originals in one offline session.

The background: Friends return from a trip with different photos on their phones. Collecting all the photos of one person means searching several galleries and asking different people to send files. Group photos make that process even more repetitive.

What SnapSync offers: SnapSync lets nearby participants choose the photos they want to share. It organizes recurring faces into common person groups, shown through face thumbnails. Anyone in the session can open a group, preview its photos and choose which originals to download. No reference selfie or automatic name assignment is needed.

Key capabilities:

  • Browse by person: Choose a face thumbnail to find photos featuring that person.
  • Share without internet: Nearby phones exchange locally stored photos within one session.
  • Send and receive together: Keep connections active while outgoing and incoming transfers overlap.
  • Choose what is shared: Only user-approved photos are offered to confirmed session members.

My contribution: Responsible for on-device face processing, grouping photos across participating devices, and integrating the offline sharing workflow.

Android Nearby Connections Face Clustering MobileFaceNet ONNX Runtime Offline Mobile System
View Architecture Flowchart & Technical Workflow ▾

How SnapSync Works: Each phone processes its own selected photos. One participant's phone acts as the coordinator and groups the combined face records. Requested original files travel directly between connected phones.

On-Device Face Processing: Detection finds faces, numerical embeddings describe faces, and complete-linkage clustering groups similar descriptions locally using a lightweight pretrained model. No cloud processing, generative AI, or active neural-network training occurs during sharing.

The AI Method in Plain Words: Detection finds faces. An embedding is a numerical face description. Clustering puts similar descriptions together. The model is pretrained; no new neural-network training or cloud processing happens during sharing.

OFFLINE ARCHITECTURE 7-Step On-Device Face Processing, Coordinator Grouping & Direct P2P Transfer

The Seven Implemented Pipeline Steps

  • 1 | Join one offline session ALL PHONES: Nearby Connections Cluster establishes confirmed direct peer-to-peer links without requiring an internet connection.
  • 2 | Select and approve local photos EACH PHONE: Android Photo Picker gives access strictly to the images each user explicitly chooses, keeping remaining gallery photos private.
  • 3 | Detect faces and align usable crops EACH PHONE: Corrects image orientation and uses ML Kit landmarks to detect faces and crop normalized facial inputs on-device.
  • 4 | Generate comparable face embeddings EACH PHONE: Lightweight MobileFaceNet executes locally via ONNX Runtime to produce compact 128D feature vectors while retaining local source-photo links.
  • 5 | Build shared person groups COORDINATOR: The session coordinator gathers face embeddings and low-resolution thumbnails from participating devices, clustering combined vectors once using pairwise cosine distance and complete linkage.
  • 6 | Browse groups and preview photos ANY PARTICIPANT: Participants browse common face groups via face thumbnails and fetch photo previews from source phones without accessing unshared photos.
  • 7 | Request originals, verify and save SOURCE / RECEIVER: High-resolution original photos are transferred directly between peers upon request, verifying SHA-256 hashes to prevent duplicates and ensure file integrity. Additional downloads can continue seamlessly within the same live session.

ClipSense

Samsung Research · March 2025

Multimodal Video Summarization & Contextual Search

AI-Powered Video Highlights & Moment Retrieval — Turn long videos into highlights and find relevant moments through contextual search.

The background: Finding a goal in a full football match or a product introduction in a long launch recording can mean repeatedly scrubbing through the video. A useful summary should show the important footage, while search should take viewers directly to the moment they need.

What ClipSense offers: The project combines DeepSeek 14B transcript summarization with YOLO object detection. It links spoken content and visible objects to source timestamps, then uses that information to create highlight videos and return relevant segments for user queries.

Key capabilities:

  • Generate video highlights: Select important sections and assemble them into a shorter video.
  • Search by context: Find moments using the subject and meaning of a request.
  • Navigate directly: Open the source video at the matching segment's timestamp.
  • Combine text and visuals: Use transcript meaning and object observations together.

My contribution: Implemented and integrated the AI pipeline: DeepSeek 14B transcript processing, YOLO object detection, and linking model outputs to timestamped video segments for highlight generation and contextual playback search.

LLM DeepSeek 14B YOLO Computer Vision Multimodal AI Video Summarization
View Architecture Flowchart & Technical Workflow ▾

How the System Works: Prepare the video once, keeping text and object observations connected to original times. The prepared information supports two output paths: highlight generation and contextual search.

The AI Method in Plain Words: DeepSeek interprets what is said. YOLO identifies visible objects. Search compares the request with prepared sections. Keeping every result linked to its original time turns AI output into playable video content.

MULTIMODAL ARCHITECTURE ClipSense: Multimodal Video Summarization & Contextual Search (7-Step Workflow)

Preparation — Shared Information Preparation

Steps 1–3 extract text and detect visible objects to build reusable, timestamped video records.

  • 1 | Read the video and timed transcript PREPARATION:
    Input: Uploaded video and available English subtitles.
    Process: Keep caption text with its original start/end times. Use speech recognition when usable subtitles are unavailable; divide long transcripts into manageable sections.
    Output: Transcript sections linked to source video times.
  • 2 | Detect visible objects PREPARATION:
    Input: Sampled video frames.
    Process: Run YOLO on each selected frame. Save detected labels, locations, confidence scores, and frame times, preserving where each observation occurred.
    Output: Timestamped object observations.
  • 3 | Prepare linked video records PREPARATION:
    Input: Timed transcript and object observations.
    Process: Join observations to text sections by time. Store their IDs and bounds; prepare exact-word search and text embeddings for comparing meaning.
    Output: Reusable records for highlights and search.

Path A — Generate Video Highlights

Steps 4–5 analyze narrative milestones to assemble a concise highlight video.

  • 4 | Select important content HIGHLIGHTS:
    Input: Transcript sections with object notes.
    Process: DeepSeek reads the surrounding text to identify important content, using object notes as context. Return concise descriptions with supporting section IDs.
    Output: Selected moments linked to original sections.
  • 5 | Build the highlight video HIGHLIGHTS:
    Input: Selected section IDs and stored source times.
    Process: Retrieve their intervals, add useful context, merge overlaps, and cut/join the source clips in time order. Retain the source references.
    Output: A shorter highlight video with traceable clips.

Path B — Find a Requested Moment

Steps 6–7 match contextual natural-language queries for instant playback navigation.

  • 6 | Match the user query SEARCH:
    Input: A request such as "S26 reveal moment."
    Process: Combine exact-name matching with text-vector similarity for related wording, such as reveal and introducing. Use object notes as supporting context when ranking candidates.
    Output: Relevant sections with their source IDs.
  • 7 | Play the relevant segment SEARCH:
    Input: The chosen section and its saved start/end.
    Process: Seek the original player to the matching interval, with a small context margin if useful. Offer alternatives or no reliable match when the request is unsupported.
    Output: Direct playback of the relevant video segment.

TabSense

Samsung Research · July 2025

BERT-Based Website Classification & Tab Organization

It reads what web pages are about and brings tabs with the same topic together.

The background: Users frequently keep dozens of browser tabs open across multiple tasks. Manually categorizing and grouping tabs into topics is tedious, while simple keyword matching struggles with varied phrasing and modern website layouts.

What TabSense offers: TabSense uses a fine-tuned BERT model to predict page topics from headings, meta descriptions, and body content. It clusters open tabs by predicted topic, presenting reviewable tab groups that users can preview, adjust, or undo.

Key capabilities:

  • Topic classification: Predict website categories from page headings and text using fine-tuned BERT.
  • Dataset preparation: Scrape and clean structured web content with Beautiful Soup across diverse topics.
  • Automatic tab grouping: Organize open tabs into coherent, labeled topic groups in the browser.
  • Reviewable organization: Preview suggested tab clusters with user corrections and stateful undo.

My contribution: Built the training dataset of ~10,000 categorized website pages using Beautiful Soup, fine-tuned the pretrained BERT model on website titles and descriptions, and integrated the offline inference pipeline for browser tab topic organization.

NLP BERT Text Classification Web Scraping Beautiful Soup Samsung Internet
View Architecture Flowchart & Technical Workflow ▾

How the System Works: TabSense operates in two phases: offline preparation (scraping website text, labeling topics, and fine-tuning BERT) and browsing-time execution (extracting text from open tabs and grouping them by predicted topic).

The AI Method in Plain Words: Beautiful Soup helps prepare website text. BERT learns and predicts topics. The browser feature places matching tabs into groups. Inference uses a saved model checkpoint without online retraining during browsing.

SYSTEM ARCHITECTURE TabSense: BERT-Based Website Classification & Tab Organization (2-Phase Workflow)

Phase A — Prepare the model before using it in the browser

Create learning examples from website content and adapt BERT using reviewed topic labels.

  • A1 | Collect useful website content with Beautiful Soup:
    Process: Python downloads web pages from categorized website links; Beautiful Soup extracts page headings, short descriptions, and main body text while filtering out menus, advertisements, and cookie controls.
    Result: Clean, readable text passages linked to their source website addresses (e.g., cricket match reports extracted into clean article text).
  • A2 | Attach the correct topic and build the dataset:
    Process: Review extracted pages, remove repeated or unusable examples, and assign the verified category label (e.g., sports report → Sports, shoe store → Shopping, programming tutorial → Education).
    Dataset structure: Each record stores the website address, heading, short description, main text, and correct topic label.
  • A3 | Train and check BERT:
    Process: Fine-tune pretrained BERT by showing it text paired with correct topic answers, adapting model representations to capture category vocabulary and context patterns.
    Partitioning: Split data into learning (~70%), validation (~15%), and final test sets (~15%) using domain-disjoint grouping so all pages from the same website stay within a single split to keep evaluation fair.
    Result: A saved, fine-tuned BERT model and input preprocessing rules ready for inference without online retraining.

Phase B — Use the prepared model on open tabs

Extract text from open tabs while browsing and arrange matching tabs into groups.

  • B1 | Read the content of the open pages:
    Process: The browser feature gathers headings, descriptions, and body text from loaded tabs using the same content extraction rules applied during dataset preparation.
    Result: Four page-text inputs prepared for each open tab.
  • B2 | Ask the saved BERT model for each topic:
    Process: BERT evaluates each tab input using its learned parameters (without online retraining) and outputs predicted topic labels (e.g., Sports, Shopping, Education).
    Result: Fast, deterministic category predictions for all readable pages.
  • B3 | Preview and group the related tabs:
    Process: The browser clusters tabs sharing the same predicted topic into organized tab groups. Users can review proposed groupings, make manual adjustments, and undo changes at any time.
    Rules: Unreadable pages remain untouched, user-defined custom tab groups are preserved, and grouping can be safely dismissed or restored.

The Core Pipeline in Plain Words: Beautiful Soup prepares and cleans website text. BERT learns and predicts topics. The browser feature places matching tabs into reviewable, labeled groups.

Offline Inference Design: Training is conducted offline to produce frozen model weights. When browsing, the browser only runs inference against the saved model—opening and organizing tabs never triggers online model training.
